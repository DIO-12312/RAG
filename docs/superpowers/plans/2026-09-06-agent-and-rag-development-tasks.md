# Agent 与 RAG 增强：简易开发任务声明

日期：2026-09-06  
状态：任务大纲，待细化实施与验收；不代表功能已经实现。

## 目标与边界

在现有个人知识库问答闭环上，提高 Agent 的稳定性、流式体验、可追溯性与检索质量。参考本地 `references/ragflow` 的设计机制，不整体迁移其工作流平台。

- Go 负责 Agent Loop、Chat Model、工具执行、上下文、引用编号和 SSE；前端负责增量展示与交互。
- Python 负责解析、切块、Embedding、检索、Rerank 和 evidence，仅通过版本化 gRPC 提供服务。
- 保留用户数据隔离、单会话选择一个知识库的现有边界；不引入多租户、Canvas、多 Agent 或通用 MCP 平台。
- 当前已有多轮工具调用和模型生成检索 query 的能力，本轮是在其上增强，不重新实现基础闭环。
- 本文是后续任务声明，不修改现行规格。实施时涉及 RPC、存储、索引语义等变化，须先核对并同步 `SPEC.md`、生成代码及相关测试。

## 执行顺序

上下文预算与真实流式输出 → 意图路由、工具执行与错误策略 → 引用完整性与运行追踪 → 检索质量优化。

每个编号作为独立工作包细化、实现和验收；过大的工作包继续拆分，不将整个阶段作为一个大提交。

## 阶段 A：上下文预算与真实流式输出

### A1：统一上下文预算

- **目标**：避免长历史和多轮检索结果累积导致模型上下文溢出。
- **任务**：在每轮模型调用前，统一预算系统提示词、工具 Schema、历史、当前问题与证据；预留输出 Token；明确模型容量及 Token 估算方式。
- **任务**：按优先级裁剪或压缩内容，保持 tool call/result 配对完整；最低必要内容仍超限时，返回明确错误。
- **验收**：覆盖长历史、大证据、多轮累积与预算不足；请求满足配置预算，消息协议不被裁剪破坏。

### A2：实现端到端真实流式输出

- **目标**：前端持续收到模型生成的增量文本，而非完成后一次性显示。
- **任务**：Go 解析上游流式响应，组装分片 tool calls，在参数完整后执行工具；通过 SSE 推送文本及终态，前端增量渲染 Markdown。
- **任务**：处理断流、取消、超时与输出中断；明确部分内容与成功消息的存储区别，避免失败内容被保存成成功回答。
- **验收**：覆盖文本和工具参数分片、首个增量到达、无重复文本、客户端取消传播及中途失败；终态只发送一次。

## 阶段 B：意图路由、工具执行与错误策略

### B0：意图路由与多轮问题准备

- **目标**：区分何时检索、复用上下文、直接回复或先澄清，避免所有消息都强制检索，同时防止知识库事实问题绕过检索。
- **任务**：由 Go 根据当前问题与有限历史识别普通交流、知识库问答、上下文追问、已有回答加工四类意图；无法确定对象或需求时进入澄清路径。

| 意图 | 示例 | 执行策略 |
|---|---|---|
| 普通交流 | “你好”“谢谢” | 直接回复，不检索 |
| 知识库问答 | “文档里怎么配置超时？” | 必须检索，以证据回答 |
| 上下文追问 | “那它有什么限制？” | 补全指代后检索；对象不明确时澄清 |
| 已有回答加工 | “把上一条总结成三点” | 复用原回答与证据；出现新增事实需求时转入检索 |

- **任务**：结合明确规则与模型结构化决策，定义 `intent`、`action`、`standalone_query`、`clarification_question` 等内部字段并校验；可复用首轮模型调用，不强制每次额外调用独立分类模型。不得仅凭问候关键词跳过同一消息中的事实问题。
- **任务**：保留原始用户问题，改写不得凭空补充实体、条件或结论；加工已有回答不得增加未经证据支持的事实或编造引用。证据快照与引用完整性由 C1 补齐。
- **任务**：分类失败或结果不合法时保守回退到检索或澄清；路由不得改变用户身份与知识库范围；取消和鉴权失败直接终止，不进入分类回退。路由调用计入 A1 上下文预算和 B2 总运行预算。
- **验收**：固定样本覆盖四类意图、混合问候与事实问题、缺失历史、歧义指代、加工中包含新增问题、恶意跳过检索指令及无效分类输出；重点统计“应检索却直接回答”的误路由，并记录额外延迟与模型调用数，实施前确定门槛。
- **边界**：B0 决定是否检索及问题的指代含义；D2 优化已进入检索路径的查询表达、候选召回和排序，不重复建设意图分类器。Python 不接管意图路由或会话策略。

### B1：统一工具注册与执行

- **目标**：解耦 Harness 与具体工具，同时保留服务端控制的安全边界。
- **任务**：建立工具注册表、参数 Schema 与执行接口；将现有 `rag_retrieve` 接入；执行前严格校验参数。
- **任务**：用户身份、知识库范围和密钥由服务端绑定；为独立只读检索增加限并发、单次超时和调用次数限制。
- **验收**：未知工具、非法参数和越权请求被拒绝；并发不突破配置；结果与 tool call ID 正确对应；取消可传播到 gRPC。

### B2：错误分类与循环收敛

- **目标**：可恢复错误允许有限调整，不可恢复错误及时终止。
- **任务**：区分参数错误、临时故障、无命中、权限拒绝、取消与总预算耗尽；将允许恢复的错误以结构化工具结果回填。
- **任务**：限制重试次数、总耗时和连续重复查询；达到轮数或预算上限时，明确收尾或失败策略，收尾调用也计入预算。
- **验收**：覆盖参数修正、临时超时、持续空结果和重复调用；不存在无限重试；取消和越权不重试；不得对未来有副作用的工具盲目重放。

## 阶段 C：引用完整性与运行追踪

### C1：完整证据与引用契约

- **目标**：引用能够准确追溯本次回答实际使用的证据。
- **任务**：贯通 Python → gRPC → Go → 前端的文档、chunk、索引版本、内容、来源定位及可用分数；明确历史引用的快照与失效策略。
- **任务**：按文档、版本和 chunk 标识组织运行内证据池，分配稳定编号；引用卡片展示对应完整 chunk；明确无证据和不足证据的回答策略。
- **验收**：覆盖跨轮去重、版本变化、未知引用编号、空召回与历史卡片；区分“编号合法”与“证据支持结论”，增加固定用例检验后者，不宣称可完全消除幻觉。

### C2：运行事件与排障记录

- **目标**：能够回答一次问答调用了什么、哪里失败、耗时和用量是多少。
- **任务**：定义 Run/Step 标识及模型调用、工具开始/结束、输出、取消和失败事件；记录耗时、Token 用量、重试次数及终止原因。
- **任务**：明确必要记录的持久化、保留期限和用户隔离；前端显示简洁执行状态；日志只保留必要的脱敏信息，不记录密钥或模型私有思维链。
- **验收**：成功、失败和取消均可关联完整运行；Token 用量不重复累计，供应商未返回时标为未知；记录不能跨用户读取。

## 阶段 D：检索质量优化

### D1：建立质量基线

- **目标**：用固定问题与证据标注判断改动收益。
- **任务**：整理直接问答、多轮指代、同义表达、代码、文档结构及无答案样本；建立 Recall@K、MRR、引用支持情况和检索耗时基线。
- **验收**：评测配置与数据版本可复现；输出优化前后对比；不使用 LLM 自由文本逐字快照作为通过标准。

### D2：优化查询、召回与 Rerank

- **目标**：减少无效查询和漏召回，提高证据排序质量。
- **任务**：承接 B0 的独立查询，评估同义表达、关键词提取等检索查询优化，保留原始问题与改写记录；明确候选数、最终 Top-K 与 Rerank Top-N 的区别；完成重排配置到 Python 执行的链路及失败策略。
- **任务**：处理 active version/删除状态复核后候选不足的问题，采用有上限的补召回；任何优化都不能绕过元数据可见性检查。
- **验收**：覆盖指代、同义查询、旧版本候选占位、Rerank 开关与故障；用 D1 基线证明收益，同时报告延迟和成本变化。实施前确定具体质量门槛。

### D3：增强文档解析与结构化切块

- **目标**：改善复杂文档和代码的证据完整性；作为独立后续工作包，不阻塞前述 Agent 交付。
- **任务**：参考 DeepDoc 思路评估 OCR、版面、表格和标题层级处理；评估 AST 代码解析，保留符号、行号及结构边界；按文件类型逐项接入。
- **验收**：使用代表性 PDF、扫描件、表格和代码 fixture 对比解析与检索效果；记录依赖及资源成本；变更解析或切块配置时明确重建索引和版本兼容策略。

## 通用交付要求

- 每个工作包交付实现、对应测试、必要接口文档及实际验证记录，说明未运行项。
- 新增或调整测试条目时同步 `tests/TEST.md`；涉及 RPC 时同步两端生成代码及契约测试。
- 索引、重试、取消等可靠性语义发生变化时，运行对应 integration/resilience 验证；检索质量变化运行固定 eval。
- 详细实施计划验收后，按仓库约定对完成并通过检查的小模块分别提交，不自动 push。
